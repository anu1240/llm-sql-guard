# LLM-SQL Guard — Schema-Grounding Hallucination Validator

Checks whether SQL generated by an LLM (Google Gemini) from a natural-language
question actually refers to real tables, real columns, and real foreign-key
relationships in a MySQL database — **before** that SQL is ever run. Queries that
pass are executed read-only and the real answer is printed; queries that fail are
blocked and the reason is explained.

## What's in here

```
db/
  01_schema.sql              -- the practice e-commerce database + hallucination_log table
  02_seed_data.sql           -- 60 customers, ~370 orders, products, reviews (dates are relative to today)
  03_validator_queries.sql   -- the validator's SQL, documented, runnable standalone
  04_readonly_user.sql       -- optional: a read-only MySQL user for the app
scripts/
  generate_seed.py           -- regenerates 02_seed_data.sql (optional)
  llm_connector.py           -- calls Gemini
  validator.py               -- the validator (parsing + INFORMATION_SCHEMA + recursive CTE)
  run_demo.py                -- asks 8 fixed questions, validates, logs, prints the analytics report
  ask.py                     -- type YOUR OWN questions (or --sql "...") and see verdict + real answer
  run_validator_tests.py     -- 43 labelled test queries; reports accuracy per failure type
  evaluate_gemini.py         -- 31 questions: Gemini's answers vs hand-written reference queries -> eval_results_<model>.md (+ eval_state_<model>.json)
  test_connection.py         -- checks .env, MySQL and Gemini one by one
.env.example                 -- copy to .env and fill in
requirements.txt
```

## One-time setup

1. **Install MySQL 8** (MySQL Workbench's bundled server is fine).
2. **Load the database** (this drops and recreates `llm_sql_guard`, including its log):
   ```bash
   mysql -u root -p < db/01_schema.sql
   mysql -u root -p < db/02_seed_data.sql
   ```
3. **Install Python dependencies:** `pip install -r requirements.txt`
4. **Get a free Gemini API key:** https://aistudio.google.com/app/apikey
5. **Copy `.env.example` to `.env`** and fill in `GEMINI_API_KEY` and your MySQL
   password. **Recommended:** run `db/04_readonly_user.sql` once (as root, after setting a
   password in it) and put that user (`guard_app`) in `.env`. The app then runs with
   read-only access plus INSERT on `hallucination_log` only; keep root for setup tasks
   such as reloading the database or `TRUNCATE TABLE hallucination_log`.

## Running it

```bash
cd scripts
python test_connection.py        # run this first
python run_demo.py               # 8 fixed questions + analytics report
python ask.py                    # type your own questions
python ask.py "your question"    # one question
python ask.py --sql "SELECT email FROM customers"   # test your own SQL, no Gemini needed
python run_validator_tests.py    # evaluation: 43 labelled queries, accuracy per failure type
python evaluate_gemini.py        # 31 questions vs reference answers (~6 min, ~31 Gemini requests)
python evaluate_gemini.py --resume   # continue a run: keeps saved answers, runs only the unanswered questions
```

The Gemini model is set with `GEMINI_MODEL` in `.env` (for example `gemini-3.8-flash`). The Gemini
free tier allows only about 20 requests per model per day, so a full 31-question run may need two
days; the evaluation saves its progress after every question, stops by itself when the daily quota
is used up, and `--resume` carries on later. Results are kept separately for each model.

Every result is logged to `hallucination_log` (use `--no-log` with the test script to skip).

## How the validator decides VALID vs HALLUCINATED

Checks run in this order (first failure wins):
1. **Table existence** — does every table in FROM/JOIN exist? (Tables defined by the
   query's own `WITH ... AS` are allowed.)
2. **Column existence** — does every column exist? Both `alias.column` and plain
   `column` forms are checked, **anywhere in the query**: SELECT, WHERE, GROUP BY,
   HAVING, ORDER BY, ON, and inside function arguments.
3. **Join validity** — every `JOIN ... ON` must use a real foreign-key column pair
   (e.g. `orders.customer_id = customers.customer_id`). If not, the recursive CTE
   explains why:
   - the tables are directly linked but joined on the wrong columns → it shows the
     correct join columns, or
   - the tables are several hops apart → it shows the real path to join through,
     e.g. `customers -> reviews -> products`.

   Extra conditions in an ON clause (`... AND oi.quantity > 1`) are fine.

**The core SQL contribution** is the recursive CTE in `db/03_validator_queries.sql`
(section D), which walks the foreign-key graph to measure how far apart two tables are
and which path connects them. Section E has the window-function analytics
(RANK, running totals, moving average) over `hallucination_log`.

## Evaluation

`run_validator_tests.py` runs 43 hand-labelled queries: 20 valid (including window
functions, subqueries, CTEs, `CASE`, `EXTRACT`), 5 made-up tables, 10 made-up columns
(including ones hidden in WHERE/GROUP BY/ORDER BY/HAVING) and 8 impossible joins
(including real tables joined on the wrong columns). Run it to see the current score.

`evaluate_gemini.py` runs 31 questions (25 with reference answers, 6 "trap" questions about data the
database does not hold) through Gemini and the validator. Results of one run per model on the same
data (details in `eval_results_<model>.md`):

| | Gemini 3.8 Flash | Gemini 2.5 Flash |
|---|---|---|
| Real questions matching the reference | 25 of 25 | 24 of 25 (one answer differs only by duplicate rows) |
| Trap: invented column, blocked by the validator | 3 | 0 |
| Trap: honest NULL placeholder | 2 | 5 |
| Trap: derived value, left for manual review | 1 | 1 |

The validator never rejected a correct query. Each model was run once, so the difference between
the models is an observation, not a measured rate.

## Known limitations

- **Structural, not semantic.** VALID means the SQL only uses things that exist and
  join correctly. It does **not** prove the query answers the question the user asked.
- **Regex + tokenizer, not a full SQL parser.** Common query shapes are handled;
  exotic syntax (e.g. `JOIN ... USING`, deeply nested derived tables, column names
  that clash with SQL keywords) may not be fully checked.
- **Unqualified columns are checked loosely:** a bare column must exist on at least
  one table in the query, not necessarily the intended one.
- The schema description sent to Gemini is built from the live database
  (`INFORMATION_SCHEMA`), so it always matches the tables; a hand-written copy in
  `llm_connector.py` is used only if the database is unreachable.
- Gemini's free tier is rate-limited and has a daily cap; the scripts retry per-minute limits
  automatically and pause between questions. If the daily cap is hit, wait until it resets.
